Fix the Closing Balance Calculation Bug
Critical Finance Immediate
Audit Finding
The report header states Closing Balance = $2,938.00, but the running balance at the most recent transaction is $362.37. The unexplained gap is $2,575.63. This is an "All Time" report so the opening balance should be $0 — making the true closing balance equal to the net movement (+$362.37), not $2,938.
Recommended Fix
  • The Closing Balance in the PDF summary header is sourced from a Firestore account balance document (a stored value), while the running balance in the table is calculated live from transaction entries. These two are out of sync.
  • The summary header should derive its closing balance from the same running balance computation as the last row in the transaction table — not from a separate document read.
  • Add a reconciliation check: if stored account balance ≠ computed running balance at report generation time, show a warning banner on the ledger page before allowing PDF export.
  • Run a one-time Firestore migration to recalculate and correct all stored account balances against their transaction histories.

Mandatory Job Card Linking for Cash Expenses
High Job Cards This Week
Audit Finding
$6,907.30 (Withdrawal — Mr Mufambisi) and $250.00 (Roll Top Ridges — Mrs Uchena) were posted as CASH expenses with no job card reference, no purpose code, and no approval trail. These represent 29.1% of total outflows that are completely unattributed.
Recommended Fix
  • In the expense / opex creation form, if account = CASH and amount ≥ $100, require one of:
       • A Job Card ID selection from open job cards, or
       • A Purpose Code from a dropdown (Wages / Supplies / Overhead / Loan Repayment / Other), or
       • An explicit "No Job Card" toggle with a mandatory description ≥ 20 characters.
  • Add a Job Card Expenses sub-tab inside each job card detail page showing all linked expenses, running total, and remaining budget.
  • On the Ledger view, highlight unlinked cash expenses > $100 in amber so they are immediately visible without running a full audit.

"Old System" / External Project Transfer Bridge
Medium Fund Transfers Backlog
Audit Finding
$4,755.50 across 7 transactions (24.5% of all outflows) was transferred to an untracked "old system" for WVZ project costs — materials, labour, transport. No corresponding WVZ revenue appears in this ledger. It is impossible to calculate the profitability of the WVZ project from this system alone.
Recommended Fix
  • Add an External Project Transfer transaction type in the Fund Transfers module with required fields: External Project Name, Cost Category (Materials / Labour / Transport / Other), and Expected Settlement Date.
  • Create an External Projects register that aggregates all transfers by project name, showing total spent, total recovered, and net position.
  • When a client payment is eventually received for an externally-tracked project, link it back to the register to close the loop — showing the full profit/loss.
  • Long term: migrate WVZ transaction history into the new system retroactively so all financial data lives in one place.

Revenue Classification Enforcement
Medium Finance This Week
Audit Finding
Mr Mabhena's $3,000.00 client payment was logged as TOPUP instead of INCOME, with no invoice or quote linked. This misclassification understates recognised revenue and makes it impossible to track the outstanding balance on this client's contract.
Recommended Fix
  • Restrict TOPUP to internal-only transactions: owner capital injections, loan receipts, and inter-account top-ups. Remove TOPUP as an option for named client payments.
  • Any payment from a named client must be linked to an Invoice ID or Quote ID. Add a client name lookup field on the payment form.
  • Add a "Part Payment" payment type that records: amount received, total invoice value, and automatically calculates and displays the outstanding balance.
  • Show an Outstanding Payments badge on each client's CRM profile page.

Transfer Charge Rate Alerting
Low Fund Transfers Backlog
Audit Finding
EcoCash transfer fee was $50 on a $1,000 transfer = 5%, exceeding the 2% audit threshold. Total bank/transfer charges were $103.34 in just 3 days. Excessive fees reduce net cash position and are not being monitored.
Recommended Fix
  • When recording a transfer with a fee, auto-calculate fee % = (fee / amount) × 100 and display it inline on the form.
  • If fee % exceeds 2%, show a warning: "This fee rate is above the 2% threshold. Consider batching transfers or using an alternative payment method."
  • Add a Monthly Bank Charges summary on the Finance dashboard showing total fees paid by account type (BANK / ECOCASH) for the current month.

Approval Gate for Large Cash Withdrawals
High HR / Access Control This Week
Audit Finding
$6,907.30 left as a single CASH withdrawal with no visible approval chain. Per the audit framework, expenses ≥ $5,000 must be verified against an authorised signatory. No such control currently exists in the system — any user can post large cash expenses without a second approval.
Recommended Fix
  • Implement a two-step approval workflow for expenses above a configurable threshold (default: $500 cash / $1,000 any account).
  • The submitter posts the expense as "Pending Approval" — it does not post to the ledger until an authorised approver (Manager / Admin role) confirms it.
  • Approvers receive an in-app notification and can approve or reject with a mandatory comment.
  • The audit trail must record: submittedBy · submittedAt · approvedBy · approvedAt · approverComment. Rejection reason is required.
  • Block the self-approval conflict of interest — submitter cannot approve their own expense. This is already flagged in the audit framework (Query 39).
